# CLAUDE.md

`SwBridge` is a fully open-source (MIT) .NET abstraction of the SolidWorks COM API. It is **MCP-agnostic**: this repo contains no application-specific integration code, no AI/agent framework code, and no business logic of any kind (licensing, subscriptions, tiers, telemetry — none of it belongs here). If a change would be useless to someone building an unrelated, non-MCP SolidWorks tool, it belongs in the consuming application instead, not here.

## Commands

```bash
dotnet build SwBridge.sln
dotnet test SwBridge.sln
dotnet run --project samples/SwBridge.Sample    # live smoke test — requires SolidWorks running
dotnet pack src/SwBridge/SwBridge.csproj -c Release -o ../localnuget
```

The pack output can be consumed from a local NuGet feed during development (add `-o ../localnuget`, or any folder, as a `<packageSources>` entry in a consuming project's `nuget.config`); the published package on nuget.org is the primary distribution channel. See "Release checklist" below for the release-pack invocation specifically.

## Architecture

- `SwDispatcher` — a dedicated STA thread with a work queue; `Run<T>(Func<T>)`/`Run(Action)` marshal arbitrary work onto it and block for the result, exception preserved. Every COM touch in the library — read and write alike — runs through it (`ADR 0003`, in this repo's `docs/adr/`), so operations against one SolidWorks session are serialized by construction, not convention. No COM dependency itself, so it is unit-tested directly (ordering, exception propagation, reentrancy, timeout, disposal). **Reentrancy**: a `Run` call made from code already executing on the dispatcher thread (e.g. one SwBridge method calling another inside its own `Run`) executes inline instead of queueing — queueing would deadlock, since the only thread that could service the queue is the one now waiting; this is deliberately a composition mechanism (every public method can dispatch independently and still nest safely), not merely a deadlock guard. **Message pump**: the worker loop waits on the work queue with a short (~10ms) timeout and pumps pending Windows messages (`PeekMessage`/`TranslateMessage`/`DispatchMessage`) whenever it comes up empty, rather than blocking on the queue indefinitely — an STA apartment that never pumps cannot service a COM call marshalled back into it from another apartment/thread, which is exactly what happens if an RCW ever leaks off the dispatcher (see `ResultConverters` below) and gets touched elsewhere; without the pump that other thread hangs forever, and because the dispatcher itself services nothing else meanwhile, every other queued `Run` call hangs behind it too. The short wait-with-timeout is a bounded wait each cycle (not a spin loop) and adds no latency to real work. **Timeout**: `Run` takes a timeout (`DefaultTimeout` = 120s unless overridden per call or via the constructor) and throws `SwDispatchTimeoutException` on the calling thread if it elapses — SolidWorks can block a COM call indefinitely (a modal dialog), and the unit of work itself cannot be aborted, only waited on with a bound; it keeps running on the dispatcher and every call still queued behind it keeps waiting for it regardless. Completion is signaled via a `TaskCompletionSource<T>` (not a disposable wait handle), because on a timeout `Run` returns while the queued work is still running and will still try to set a result later — a `ManualResetEventSlim` would be unsafe to dispose in that case. **Disposal**: `Dispose()` joins the thread with a bounded timeout (`DefaultDisposeTimeout` = 5s) rather than indefinitely, for the same wedged-call reason; `IsFullyStopped` reports whether the join actually completed.
- `SwConnection` — owns the `SwDispatcher` (`.Dispatcher`); lazy attach to the running `SldWorks.Application` via `oleaut32!GetActiveObject`, run on that thread; liveness-checks the cached RCW on every access (`IsAlive` catches `COMException`, `InvalidCastException`, and `InvalidComObjectException` — the last is what a disconnected RCW throws, e.g. after a converter or another holder released it; missing it used to mean the one mechanism that exists to recover from a dead COM link couldn't recover from that particular kind of dead) and re-attaches if SolidWorks was closed/restarted. Never launches SolidWorks. `GetApp()` is still a direct, synchronous return of the raw `ISldWorks` — the deliberate raw escape hatch for advanced consumers — so a caller using it from a thread other than the dispatcher's own is doing the exact cross-apartment access `ADR 0003` exists to avoid; SwBridge cannot prevent that for raw consumers, only route its own calls correctly.
- `DocumentManager` — enumerate/resolve/open documents, plus `NewPart(templatePath?)` (creates from a template, or SolidWorks' configured default template via `swUserPreferenceStringValue_e.swDefaultTemplatePart` when omitted — pattern verified live against a real SolidWorks install). Every method wraps its body in one `Dispatcher.Run` call. Throws `SwNotRunningException` (rather than returning empty) so callers can distinguish "no SolidWorks" from "no documents". `Resolve` throws `SwBridgeException` when a name matches more than one open document rather than silently returning the first match — an ambiguous *write* target is worse than a reported error (see README's Design notes for the full rationale).
- `SwDocument` — wrapper so consumers rarely touch interop types; raw `ModelDoc2` stays exposed via `.Model` (same raw-escape-hatch caveat as `SwConnection.GetApp()`). Every method dispatches via the `SwDispatcher` it was constructed with.
- `ModelInspector` — generic feature-tree reading. The central rule: **no feature type is hardcoded**. Callers pass a `Func<string, IReadOnlyList<string>?>` mapping feature type name → property names, and properties are read off `IFeature.GetDefinition()` by reflection (`ComPropertyReader`). `GetFeatures` releases both the feature and its definition RCW per iteration (was previously leaking both — fixed alongside `DescribeFeatureDefinition`, which already did this correctly and is the pattern this now matches).
- `ComPropertyReader` — `Type.InvokeMember(..., GetProperty | IgnoreCase)` against late-bound COM objects; unreadable properties are reported as absent, never thrown. Read-only, by design (combined flags).
- `ComTypeInspector` — discovers the real members of a late-bound COM object, so a caller can find the member names/signatures to put in a `PropertySpec` instead of guessing. Two independent, complementary mechanisms:
  - `DescribeMembers` reads `ITypeInfo` reached via `IDispatch::GetTypeInfo`, falling back to `IProvideClassInfo` (which recovers real data for creatable coclasses like `ModelDoc2`/`PartDoc` — verified live, 175 members) since many SolidWorks objects answer `GetTypeInfoCount()` with 0 despite being dual interfaces. Some internal SolidWorks objects — notably `IFeature` and the feature-definition objects from `IFeature.GetDefinition()` — implement neither and are not introspectable at all this way (verified live against `Boss-Extrude1`'s `IExtrudeFeatureData2`); it returns an empty list for those, which means "not introspectable via `ITypeInfo`," not "no members" — `ComPropertyReader`'s name-based invocation still works on them.
  - `FindImplementedInteropInterfaces`/`DescribeMembersViaInterop` are the fallback that covers exactly that gap: they probe the live object with a real COM QueryInterface against every `[ComImport]` interface declared in the referenced `SolidWorks.Interop.sldworks` assembly (`typeof(ISldWorks).Assembly`, via `Type.IsInstanceOfType`), then reflect whichever interfaces actually matched. Verified live: this recovers `Boss-Extrude1`'s `IExtrudeFeatureData`/`IExtrudeFeatureData2`, including `GetDepth` as a method with 1 param. An unfiltered probe (`filter: null`) walks a few thousand interfaces — each a cross-process QueryInterface — and, because these methods do no dispatching themselves, an unfiltered call made from inside a `SwDispatcher.Run` monopolizes the shared dispatcher for its whole duration, blocking every other queued operation. `ComTypeInspector.FeatureDataFilter` is a public, reusable, filtered-by-default predicate (interface name contains `"FeatureData"`, ~100 candidates instead of a few thousand) for the common case; `ModelInspector.DescribeFeatureDefinition` uses it when falling back to this after `DescribeMembers` finds nothing. Prefer it, or a narrower filter of your own, over an unfiltered call.
  - `DescribeAllMembers` is the union of both, deduplicated by `(Name, Kind, ParamCount)`, for objects where the two are not redundant — the case that motivated it: a document root (`ModelDoc2`/`PartDoc`) answers `DescribeMembers` via `IProvideClassInfo`'s coclass default interface (175 members, non-empty, so the either/or fallback in `DescribeFeatureDefinition` would never reach the interop probe), but that default interface omits `IModelDoc2` members like `EditRebuild3`/`SaveAs3`/`EditUndo2`/`ClearSelection2` — found live: `DescribeMembers` alone reports 175 members and misses all four; `DescribeAllMembers` reports 947 and finds all four, with correct kinds/param counts (`EditRebuild3`: Method/0, `SaveAs3`: Method/3, `EditUndo2`: Method/1, `ClearSelection2`: Method/1). `interopFilter` defaults to `null` (unfiltered) — this method takes no position on the filtering tradeoff; that policy call belongs to the caller. The existing methods and `DescribeFeatureDefinition`'s either/or fallback are unchanged; this is a new, opt-in entry point.
- `SelectionInspector` — `GetSelection(ModelDoc2)` reads what is currently selected as `SelectionInfo { Type, Descriptor }` DTOs (`ISelectionMgr.GetSelectedObjectCount2(-1)`/`GetSelectedObjectType3(i, -1)`/`GetSelectedObject6(i, -1)`, 1-based `i` — verified live). `Type` is the `swSelectType_e` name; `Descriptor` is a best-effort, human-meaningful identity (edge: curve kind + chord length + chord midpoint from the edge's vertices; face: surface kind + area + bounding-box-midpoint center; vertex: the point; named entities: the name), never a live reference and never a reason to fail the whole read. This exists to close the "silent wrong-edge" failure: `DocumentStateProbes.GetSelectionCount` says *how many*, never *what* — a selection-driven write (fillet, chamfer, draft) can succeed against the wrong entity with no COM error at all. Verified live against a known 20 mm box edge: `length=0.02 m, midpoint=(0.05, 0.05, 0.01) m`, exact. Deliberately does **not** use `IEdge.GetCurveParams2()` + `ICurve.GetLength2`/`Evaluate2` despite that looking like the documented API for this — verified live that `GetCurveParams2()`'s array is not the simple start/end-parameter pair its name implies (its first six values matched the edge's start/end vertex coordinates instead of curve parameters), and feeding it to `GetLength2`/`Evaluate2` produced nonsense (a negative length; a midpoint off the edge). Vertices are the mechanism that actually worked live, so that is what ships.

### Write surface (`ADR 0001`/`0002`/`0003`, in this repo's `docs/adr/`)

- `ComInvoker` — the **only** write-dispatch door: `InvokeMethod`/`GetProperty`/`SetProperty`, each exactly one COM dispatch flag, **never combined** — the deliberate contrast with `ComPropertyReader`'s combined read-only flags. Returns a typed `InvokeOutcome { Success, Value, FailureDetail }` instead of throwing for a member-level failure, because SolidWorks write APIs report most failures as `Nothing`/`False`, not exceptions. Verified live: a `null` argument for a COM-interface-typed parameter (e.g. `SelectByID2`'s `Callout`) needs `new DispatchWrapper(null)`, not a bare `null` — late-bound `Type.InvokeMember` has no compile-time parameter types to coerce against, and a bare `null` marshals as `VT_EMPTY`, which SolidWorks rejects with `DISP_E_TYPEMISMATCH`.
- `ComPath` — open, dotted, **strictly read-only** path resolution (`"Extension.SelectionManager"`) from an application or document root, one hop per segment via `ComPropertyReader.TryGetPropertyStrict` — `DISPATCH_PROPERTYGET` only, never `ComPropertyReader.TryGetMember`'s combined `GetProperty | InvokeMethod` flags used by the feature-definition read path. This is load-bearing: with the combined flags, a path segment that happened to name a zero-argument COM method (`ExitApp`, `EditDelete`, …) would be silently *invoked* while merely being resolved — a real defect found in review and fixed by giving `ComPath` its own strict reader rather than reusing `ComPropertyReader`'s. Deliberately an open grammar, not a closed enum of known targets (`ADR 0001`): a bad path is a runtime `ComPathResult` failure, not a schema error, so a newly discovered manager object never needs a SwBridge release before it can be addressed.
- `ResultConverters` — `ToFeatureRef`/`ToSketchSegmentRef`/`ToSketchSegmentRefs` turn a live COM return into a plain, serializable DTO (`FeatureRef`, `SketchSegmentRef`); a live interface pointer must never survive past the call that produced it. Each takes an `ownsReference` flag (default `true`) controlling whether the RCW is released after conversion — `Marshal.ReleaseComObject` on an object something else still holds a reference to *disconnects* it for every holder, not just the caller, permanently (`InvalidComObjectException` from then on). Default `true` matches the common case (a fresh write-call return, e.g. `FeatureExtrusion3`'s `IFeature`); pass `false` for anything resolved rather than freshly created — e.g. `Extension.Document` is the same COM identity as `SwDocument.Model`. Verified live: `ISketchSegment.GetID()`'s interop signature says bare `object`, but it actually returns `int[]` (a composite id) — `SketchSegmentRef.Id` is that array's first element.
- `DocumentStateProbes` — cheap, targeted reads (`GetFeatureCount`, `IsInSketchMode`, `GetSketchSegmentCount`, `GetSelectionCount`, `NeedsRebuild`) plus one active probe (`RebuildSucceeded`, which forces `EditRebuild3()` since SolidWorks exposes no passive rebuild-error-count getter) — the vocabulary `ADR 0002`'s write-step verification and `ADR 0001`'s preconditions are built on. Take an already-resolved `ModelDoc2`; no dispatching themselves. Each probe releases the intermediate COM objects it reaches through the document (`FeatureManager`, `SketchManager`, `ActiveSketch`, `SelectionManager`, `Extension`) before returning — a write step takes several of these per call (precondition + pre-snapshot + post-verify + result snapshot), and unreleased native references accumulate fast enough at MCP-session timescales to make SolidWorks refuse to fully close a document afterward.

## Rules

- **No console output from library code** — consumers include stdio-based servers where stdout is a protocol stream.
- Public API avoids leaking interop types where practical; where they appear (`SwDocument.Model`, `SwConnection.GetApp()`, `ModelInspector` parameters) it is deliberate, for advanced consumers — and, per `ADR 0003`, using them off the dispatcher thread is the caller's own cross-apartment risk to manage.
- All COM access goes through `SwDispatcher`; do not touch a COM object from a thread you did not get via `SwDispatcher.Run`.
- Tests in `tests/SwBridge.Tests` must run **without** SolidWorks installed. Anything needing a live instance goes in `samples/` (currently `SwBridge.Sample`, which doubles as the manual smoke test; the default run is read-only — `--new-part`, `--selection-demo` and `--document-discovery` each opt into something that either writes (the first two, each creating and closing its own scratch part) or is merely slow (the third: an unfiltered interop probe)).
- Interop packages: `SolidWorks.Interop.sldworks` / `SolidWorks.Interop.swconst` 32.1.0 (SW 2024 interop). SwBridge is late-bound almost everywhere, so it is *expected* to work against SolidWorks 2021+, but has been live-tested only against SolidWorks 2026 SP3.0 — see README's Requirements section for the honest version claim and the interop-dependency disclosure (`$(SolidWorksApiRedist)` escape hatch, `docs/THIRD-PARTY-NOTICES.md`).

## Release checklist

Do these in order, every release. Skipping the clean-tree check is exactly how the 0.5.0
localnuget pack ended up non-reproducible (its nuspec `commit` pointed at the wrong commit) —
this section exists so that does not happen again.

1. **Land every change as a commit.** Everything the release should contain — code, version
   bump, docs — committed on `main`.
2. **Verify a clean tree**: `git status` must report nothing to commit, nothing untracked that
   should be tracked. A pack from a dirty tree embeds whatever the working directory happened to
   contain, not what the commit says it contains — SourceLink and the nuspec `commit` field both
   become misleading.
3. **Pack with `ContinuousIntegrationBuild` set**, so SourceLink/deterministic-build tooling
   knows this is a release artifact, not a local dev build (this suppresses embedding local
   absolute paths and other machine-specific state):
   ```bash
   dotnet build SwBridge.sln            # full build + test gate first, 0 warnings
   dotnet test SwBridge.sln
   dotnet pack src/SwBridge/SwBridge.csproj -c Release -o ../localnuget -p:ContinuousIntegrationBuild=true
   ```
4. **Verify the produced package**, before pushing anywhere:
   - Unzip the `.nupkg` (it is a zip) and confirm `lib/` contains only `SwBridge.dll`/`.xml` (no
     interop DLLs — SwBridge depends on them, it does not redistribute them) and that `README.md`
     is present at the package root.
   - Open the `.nuspec` inside it and confirm the `<repository>` element's `commit` attribute
     equals the output of `git rev-parse HEAD` run *before* packing. If it does not match, the
     tree was dirty (or you packed the wrong commit) — fix and repack; do not publish.
   - Confirm `<license type="expression">MIT</license>`, `<copyright>`, and `<projectUrl>` are all
     present.
   - Confirm a matching `.snupkg` (the symbol package) was produced alongside the `.nupkg`.
5. **Only then** `dotnet nuget push` (nuget.org) and `git push` (GitHub) — in either order, but
   both only after step 4 passes. Never publish a package you have not unzipped and checked.
